## 1. ChatGPT

可以，但细粒度有明显层级。对于你前面说的 **“视频抽帧 → CLIP embedding → Text → Frame Retrieval”**，一个比较实用的判断是：

 | Text 想描述的内容 | 单帧 CLIP 召回能力 | 例子 |
| --- | --- | --- |
| 场景 | 强 | a beach at sunset、inside a supermarket |
| 明显物体 | 强 | a red car、a person holding an umbrella |
| 衣着大类/颜色 | 中-强 | a man wearing a black suit、a woman in a red dress |
| 人物正在做的明显动作 | 中-强 | running、riding a bicycle、playing basketball |
| 人物角色/职业 | 中等 | a chef、a police officer、a doctor |
| 明显表情 | 中等 | smiling、crying、laughing |
| 细粒度动作 | 弱-中 | picking up vs putting down |
| 细微神态/心理状态 | 弱 | nervous、confused、embarrassed |
| 时间关系 | 很弱/基本做不了 | stands up after sitting |
| 复杂组合/空间关系 | 不稳定 | the man left of the woman holding a cup |

 CLIP 官方也明确指出，它对常见视觉概念很强，但对**计数、复杂关系和非常细粒度分类**明显更弱，而且结果还会受到文本措辞影响。[![image](https://www.google.com/s2/favicons?domain=https://openai.com&sz=128)OpenAI](https://openai.com/index/clip/?utm_source=chatgpt.com)

 ## 1. “动作”到底能细到什么程度？

 这里要先分两种动作。

 ### 第一种：一张照片本身就能看出来的动作

 例如：

```
a man running
a woman riding a bicycle
a person smoking
a man drinking water
a woman talking on the phone
a person playing basketball
a man holding a gun
a person typing on a keyboard
```

 这些其实不是特别依赖“时间”，因为**单张静态图片就包含很强的视觉线索**。

 例如：

```
       🧍
      /  \
     🏀
     ↓

弯曲的身体姿态
+ 篮球
+ 球场
+ 手的位置
```

 CLIP 从这些联合视觉特征可以推测：

```
"playing basketball"
```

 所以这一类通常比较好。

 原始 CLIP 本身甚至已经做过 UCF101 这样的动作识别 zero-shot 测试，说明预训练的图文空间确实包含一定的动作语义。[![image](https://www.google.com/s2/favicons?domain=https://arxiv.org&sz=128)arXiv](https://arxiv.org/pdf/2103.00020?utm_source=chatgpt.com)

---

 ### 第二种：必须看连续过程才能知道的动作

 例如：

```
"picking up a cup"
```

 和：

```
"putting down a cup"
```

 某一瞬间可能都是：

```
人 + 手 + 杯子
```

 单帧根本不知道：

```
上一秒：

手 → 杯子

还是：

杯子 → 桌子
```

 类似还有：

```
opening the door
vs
closing the door

sitting down
vs
standing up

entering the room
vs
leaving the room

throwing a ball
vs
catching a ball
```

 这不是 CLIP “模型不够大”这么简单，而是：

 > **输入的一张图片本身就缺少时间信息。**

 所以对于视频，如果你需要这种粒度，就应该从：

```
Frame → CLIP
```

 升级到：

```
Frames(t-2 ... t+2)
       ↓
Temporal / Video Encoder
       ↓
Video embedding
```

 这也是为什么后来出现 ActionCLIP 这类方法：它不是只把单帧当图片，而是专门考虑视频动作表示。[![image](https://www.google.com/s2/favicons?domain=https://arxiv.org&sz=128)arXiv](https://arxiv.org/abs/2109.08472?utm_source=chatgpt.com)

 # 2. 角色能到什么程度？

 例如：

```
a doctor
a chef
a police officer
a firefighter
a construction worker
a basketball player
```

 通常可以有不错效果。

 但 CLIP 其实是在利用：

```
人物外观
+
衣服
+
工具
+
环境
```

 推断这个概念。

 例如：

```
白大褂
+ 听诊器
+ 医院
        ↓
    "doctor"
```

 所以：

```
a doctor wearing a white coat
```

 通常可能比单独：

```doctor
doctor
```

 更容易匹配。

 但是：

```
一个穿普通 T 恤坐在家里的医生
```

 你搜：

```doctor
doctor
```

 CLIP **没有理由知道他是医生**。

 所以角色检索实际上更准确地说是：

 > **检索具有该角色典型视觉特征的人。**

 而不是理解这个人的真实社会身份。

 # 3. 神态 / 表情呢？

 这里也是很明显的层级。

 比较容易：

```
smiling
laughing
crying
angry face
surprised expression
```

 困难很多：

```
slightly nervous
embarrassed
hesitant
skeptical
confused
contemptuous
pretending to smile
```

 特别是你的视频画面是：

```
1920×1080
```

 但人的脸只占：

```
40×40 pixels
```

 那即使模型能力再强：

```
整张 Frame
   ↓ resize
224×224
   ↓
CLIP
```

 脸可能只剩十几个像素。

 这时：

```
"smiling person"
```

 都可能不稳定。

 这也是专门的 facial-expression vision-language 模型能明显超过 vanilla CLIP 的原因。比如 EmoCLIP 在视频表情识别任务上报告了相比基础 CLIP 明显的改进，说明**通用 CLIP 并不是为细粒度表情专门优化的**。[![image](https://www.google.com/s2/favicons?domain=https://arxiv.org&sz=128)arXiv](https://arxiv.org/abs/2310.16640?utm_source=chatgpt.com)

 # 4. 衣着其实是比较适合 CLIP 的

 例如：

```
a man wearing a black suit
a woman wearing a red dress
a person wearing a yellow jacket
a man in a white T-shirt
a woman wearing jeans
a person wearing a baseball cap
```

 通常比较靠谱。

 甚至可以进一步：

```
a man wearing a black leather jacket
```

```
a woman wearing a long white dress
```

```
a person wearing a striped shirt
```

 但是越来越细后会下降：

```
a shirt with three small buttons
```

```
a jacket with a zipper on the left pocket
```

```
a shirt with a 2 cm blue logo
```

 原因很直接：

```
人物在整个视频 Frame 中太小
        ↓
细节没有足够像素
        ↓
CLIP preprocessing 又缩放
        ↓
视觉 encoder 根本看不清
```

 # 5. 所以真正决定“细粒度”的第一大因素：目标占画面的大小

 这是做你这个视频系统时**非常关键**的一点。

 假设同一个人：

 ### Frame A

```
┌────────────────────────────┐
│                            │
│          🧍                │
│                            │
│                            │
└────────────────────────────┘

人物只占画面 5%
```

 你搜：

 > `a man wearing glasses and a black jacket`

 效果可能很差。

 但如果首先做人检测：

```
Frame
  ↓
YOLO / GroundingDINO / detector
  ↓
Person crop
```

 得到：

```
┌─────────────┐
│    👨🏻‍🦱    │
│    👓       │
│    🧥       │
│             │
└─────────────┘
```

 再：

```
Person crop
     ↓
   CLIP
```

 召回：

```
"man wearing glasses"
"man in a black jacket"
```

 往往会明显更合理。

 所以你最终甚至可能做成**多级 embedding**：

```
一个 Video Frame
       │
       ├── Global Frame embedding
       │
       ├── Person #1 embedding
       │
       ├── Person #2 embedding
       │
       ├── Car embedding
       │
       └── Object embeddings
```

 这样：

```
"an office with many computers"
           ↓
Global Frame Index
```

 而：

```
"a man wearing glasses and a blue shirt"
           ↓
Person Index
```

 就完全不一样了。

 # 6. 第二个核心因素：你选择的 CLIP 模型

 `clip-as-service` 本身只是 serving framework。

 里面真正决定 embedding 质量的是：

```
CLIP model
```

 项目代码现在能看到支持很多不同模型，例如：

```
ViT-B-32
ViT-B-16
ViT-L-14
ViT-L-14@336
ViT-H-14
ViT-g-14
```

 以及 OpenAI / LAION 等不同预训练权重。[![image](https://www.google.com/s2/favicons?domain=https://github.com&sz=128)GitHub+1](https://github.com/jina-ai/clip-as-service/blob/main/server/clip_server/model/clip_onnx.py?utm_source=chatgpt.com)

 大致可以理解为：

```
ViT-B/32
   ↑
速度快
计算量低
细节能力较弱

ViT-B/16
   ↓
更细 patch

ViT-L/14
   ↓
更大模型

ViT-L/14@336
   ↓
更高输入分辨率

ViT-H/14 / g/14
   ↓
更大
```

 但并不能简单理解为：

 > 模型越大 = 所有细节都能理解。

 更核心的是：

```
模型容量
×
输入分辨率
×
训练数据
×
训练目标
```

 共同决定。

 # 7. 第三个非常重要的因素：训练数据里有没有这种概念

 CLIP 本质上是通过海量：

```
image ↔ caption
```

 学习概念。

 例如互联网中：

```
"a woman wearing a red dress"
```

 这种 caption 大量存在。

 所以：

```
red dress
```

 很容易形成稳定语义。

 但是例如非常专业：

```
"a worker operating model ABC-218 hydraulic valve"
```

 训练集中可能很少。

 模型就很难。

 有研究专门分析了这一点：下游 zero-shot 能力与相关概念在预训练图文数据中出现的频率有明显关系。[![image](https://www.google.com/s2/favicons?domain=https://arxiv.org&sz=128)arXiv](https://arxiv.org/pdf/2404.04125?utm_source=chatgpt.com)

 所以如果你的视频来自特殊领域：

```
普通互联网视频
```

 和：

```
工业监控
医学手术
半导体工厂
军事装备
专业体育
```

 CLIP 的能力会非常不同。

 # 8. 第四个问题：一句话塞很多条件，不代表 CLIP 会严格 AND

 这点对你想做的搜索系统尤其重要。

 比如你输入：

 > **a young man wearing a black jacket, smiling, holding a red umbrella, standing beside a white car**

 里面实际上有很多条件：

```
man
AND
black jacket
AND
smiling
AND
red umbrella
AND
white car
```

 你可能以为 CLIP 会进行数据库式：

```
A ∩ B ∩ C ∩ D ∩ E
```

 实际上不是。

 它做的是：

```
整个 sentence
       ↓
一个 embedding
       ↓
cosine similarity
```

 所以结果可能是：

```
结果 A：
黑衣男子 + 红伞
没有汽车

结果 B：
男子 + 白车
没有伞

结果 C：
红伞 + 白车
人物穿的是蓝色衣服
```

 但 embedding 都可能很接近。

 也就是说：

 > **CLIP 是 semantic similarity，不是逻辑查询引擎。**

 原始 CLIP 官方也特别指出模型对一些复杂任务、细粒度区分和 prompt wording 会比较敏感。[![image](https://www.google.com/s2/favicons?domain=https://openai.com&sz=128)OpenAI](https://openai.com/index/clip/?utm_source=chatgpt.com)

 # 9. 这就引出了你这个项目很重要的一种架构

 如果你真的希望用户能够搜索这种：

 > **“找穿黑色上衣、戴眼镜、正在打电话，并且旁边有汽车的男性”**

 单纯：

```
一句 Text
   ↓
CLIP
   ↓
一个 vector
```

 可能不够。

 更好的系统是：

```
Query
"man wearing black clothes,
 glasses, talking on phone,
 next to a car"
              ↓
         Query Parser
              ↓
 ┌────────────┼─────────────┐
 ↓            ↓             ↓
person     clothing       action
man        black          phone
 ↓            ↓             ↓
glasses                    ↓
              ↓
          object/context
             car
```

 然后：

```
CLIP semantic retrieval
         ↓
      Top 1000
         ↓
 VLM / Cross Encoder rerank
         ↓
       Top 50
```

 这往往比：

```
CLIP Top-50
```

 效果好很多。

 ## 最重要的一句话

 对于你现在考虑的 **视频 Text → Frame 搜索系统**：

 > **CLIP 能达到的细粒度上限，不主要取决于“Text 能写多详细”，而取决于这些细节是否真的能从这一帧视觉上辨认出来，以及模型训练时有没有学会把这种视觉模式和语言概念对齐。**

 所以：

```
Text detail
   ↓
不等于
retrieval detail
```

 真正是：

```
最终检索细粒度
≈
模型能力
× 预训练数据覆盖
× 图像分辨率
× 目标在画面中的大小
× 静态可观察性
× prompt 表达
× domain match
× retrieval / rerank pipeline
```

 如果你现在真准备基于 `clip-as-service` 搭这个系统，我比较建议下一步不要只讨论“CLIP 能不能搜”，而是直接设计成 **Video → 抽帧 → global embedding + person/object crop embedding → Vector DB → CLIP Recall → VLM Rerank**。这种架构会比“所有帧各存一个 CLIP vector”强非常多，而且可以具体分析它能支持到怎样的 **人物 / 行为 / 衣着 / 神态组合检索**。

 ## 1. 中文到底能做到什么程度？

 如果直接用最原始的 OpenAI CLIP：

```
中文 query
   ↓
原始 CLIP text encoder
   ↓
效果通常不理想
```

 因为原始 CLIP 的语言侧主要围绕英文互联网图文数据训练。

 但换成中文/多语言模型以后，工作流完全一样：

```
视频帧 ─────→ Image Encoder ──→ vector
                                 │
中文 Query → Text Encoder  ──→ vector
                                 │
                          cosine similarity
                                 ↓
                            Top-K 视频帧
```

 例如用户直接输入：

 > “一个穿黑色夹克戴眼镜的男人正在打电话”

 是可以直接作为中文 query 的，不需要先翻译成英文，只要你选择的是中文/多语言模型。

 Chinese-CLIP 就是专门为这个问题做的，它用约 **2 亿中文图文对**训练。其官方报告中，最优规模模型在 MUGE 中文 text→image zero-shot 检索上达到 R@1 **63.0%**、R@5 **84.1%**、R@10 **89.2%**；Flickr30K-CN text→image zero-shot 为 R@1 **71.2%**、R@5 **91.4%**、R@10 **95.5%**。[![image](https://www.google.com/s2/favicons?domain=https://github.com&sz=128)GitHub+1](https://github.com/OFA-Sys/Chinese-CLIP?utm_source=chatgpt.com)

 不过 Chinese-CLIP 本身也已经是上一代方案了。

 ### Jina CLIP v2

 这是和你现在看的 Jina 项目最自然的现代替代。

 它是约 **0.9B 参数**，图像输入提升到 **512×512**，支持 **89 种语言，包括中文**，输出最多 1024 维，而且支持 Matryoshka，可以缩到 64/128/256 等维度。[![image](https://www.google.com/s2/favicons?domain=https://huggingface.co&sz=128)Hugging Face+1](https://huggingface.co/jinaai/jina-clip-v2?utm_source=chatgpt.com)

 # 9. 为什么是“embedding 召回 + VLM rerank”？

 假设用户搜：

 > **“一个穿黑色夹克的男人摘下眼镜，然后开始打电话。”**

 单帧 embedding 很容易只找到：

```
男人
黑色夹克
眼镜
手机
```

 却不保证：

```
摘下眼镜
然后
开始打电话
```

 所以：

```embedding
Embedding
```

 负责高速地从：

```
10,000,000 frames
```

 缩到：

```
Top 200
```

 然后：

```qwen3-vl
Qwen3-VL
```

 才负责：

```
哪个片段真的符合：
“摘眼镜 → 打电话”
```

 这样成本才能接受。

 完整思路就是：

```
        Recall                         Precision

10M frames
    ↓
Embedding ANN
    ↓
Top 500
    ↓
metadata/filter
    ↓
Top 100
    ↓
VLM Reranker
    ↓
Top 10
```

 这其实也是现在搜索系统里非常典型的两阶段结构。

 # 11. 真正大规模以后，GPU 反而不一定是唯一问题

 例如有：

```
1000 小时视频
1 FPS
```

 帧数量：

```
1000 × 3600
= 3,600,000 frames
```

 假设 embedding 是：

```
1024 dim
FP16
```

 每条约：

```
1024 × 2 bytes
= 2KB
```

 那么原始向量：

```
3.6M × 2KB
≈ 7.4 GB
```

 这很小。

 但是到了：

```
10,000 小时
```

 就是：

```
36M vectors
≈ 74 GB raw embeddings
```

 如果 Vector DB 用 FP32：

```
≈ 147 GB
```

 再加：

```
HNSW / IVF index
metadata
thumbnail
object crop embeddings
```

 很容易几百 GB。

 而最容易被忽略的是**缩略图**。

 如果 3600 万帧，每张 JPEG 即使只有 30KB：

```
36M × 30KB
≈ 1.08 TB
```

 所以实际系统经常：

```
vector 保存
+
video_id
+
timestamp
```

 而不是把每个 frame JPEG 永久保存。

 需要的时候：

```
ffmpeg -ss timestamp
```

 再从原视频生成预览。

 # 二、为什么不选 Jina CLIP v2？

 Jina CLIP v2 其实仍然很好。

 它只有约 0.9B 参数，支持中文在内的大量语言，图像分辨率提升到 512×512，而且专门强调更好地捕捉 fine-grained visual elements。[![image](https://www.google.com/s2/favicons?domain=https://huggingface.co&sz=128)Hugging Face+1](https://huggingface.co/jinaai/jina-clip-v2?utm_source=chatgpt.com)

 所以它非常适合：

```
吞吐优先
成本优先
海量图片 embedding
简单场景/物体/服装搜索
```

 但你的要求是：

 > **尽可能准确捕捉动作、神态、衣着类型以及多个属性组合。**

 这时候我更看重模型的视觉语义能力，而不是每秒多编码几十张图片。

 因此定位应该是：

```
Qwen3-VL-Embedding-8B
        ↓
主模型 / 最终生产候选

Jina CLIP v2
        ↓
轻量 baseline / 性能对照
```

 SigLIP 2 也是非常好的 baseline，Google 在 SigLIP 2 中强化了多语言、定位和 dense feature 能力，并且在多个尺度下超过第一代 SigLIP，但从你这个具体项目看，目前 Qwen3-VL-Embedding 的整套 Embedding + Reranker 组合更完整。[![image](https://www.google.com/s2/favicons?domain=https://arxiv.org&sz=128)arXiv](https://arxiv.org/abs/2502.14786?utm_source=chatgpt.com)

---

 # 三、但只换成一个更大的 Embedding 模型仍然不够

 这是整个方案最重要的一点。

 假设视频的一帧是：

```
3840 × 2160

┌────────────────────────────────────────────┐
│                                            │
│                   👨                       │
│                                            │
│       桌子              汽车               │
│                                            │
│                                            │
└────────────────────────────────────────────┘
```

 一个人可能只占整个画面：

```
8% × 20%
```

 你希望搜索：

 > “穿黑色夹克、戴眼镜、正在打电话、略带微笑的男性”

 如果直接：

```
整张 4K Frame
       ↓ resize/tokenize
Qwen3-VL-Embedding
```

 即便模型非常强，脸和眼镜仍然可能只是几个视觉 token。

 所以真正决定你的系统能不能搜：

 > “微笑 + 眼镜 + 黑色夹克 + 打电话”

 的关键并不是单独换模型，而是：

 > **多尺度 / 多视图 Embedding。**

 我建议一张 Frame 不只存一个向量，而是存多种视觉视角。

 # 五、一张图片到底生成哪些 embedding？

 这是我建议固定下来的四种。

 ## 1. Global Frame

 整张视频帧：

```
┌──────────────────────────┐
│     人       汽车        │
│                          │
│        道路              │
│                          │
└──────────────────────────┘
```

 主要负责：

```
场景
环境
人物角色
人与物体关系
明显动作
整体事件语义
```

 例如：

 > “一个男人站在汽车旁边”

 > “办公室里有人坐在电脑前”

 > “篮球场上的球员正在投篮”

---

 # 六、Person Context Crop

 这个非常重要。

 检测到：

```
      ┌───────┐
      │  人   │
      │       │
      └───────┘
```

 不要只裁人，而是把 bbox 向外扩：

```
1.25x ～ 1.5x
```

 得到：

```
┌────────────────┐
│                │
│      👨 📱      │
│                │
│       🪑        │
└────────────────┘
```

 这样模型还能看到：

```
身体姿态
+
手里的手机
+
附近物体
+
一部分环境
```

 这是**动作搜索最重要的视图**。

 例如：

 > 正在打电话

 > 正在喝水

 > 正在拿包

 > 正在看手机

 > 正在使用电脑

 如果裁得太紧：

```
只剩人体
```

 手机、杯子等关键 object 很可能被裁掉。

 所以：

 > **Action → Person Context**

 应该成为第一优先索引。

---

 # 七、Person Tight Crop

 同时保存一个比较紧的人体 Crop：

```
┌──────────┐
│    👨    │
│   👕     │
│   👖     │
│          │
└──────────┘
```

 这个视图主要负责：

```
衣着类型
衣服颜色
服装纹理
帽子
眼镜
背包
身体姿态
人物粗粒度外观
```

 例如：

 > 黑色西装

 > 蓝色牛仔外套

 > 白色短袖 T 恤

 > 红色连衣裙

 > 戴棒球帽的人

 > 穿长款羽绒服的人

 对于你的“衣着类型”要求，这个索引通常会明显优于 Global Frame。

---

 # 八、Face Crop

 如果检测到足够大的脸：

```
┌────────┐
│  😄    │
└────────┘
```

 单独生成 embedding。

 主要承担：

```
smiling
laughing
crying
surprised
angry
neutral
```

 等比较明显的表情。

 但这里需要明确边界：

 > Qwen3-VL-Embedding 是通用多模态检索模型，不是专业 Facial Expression Recognition 模型。

 所以：

```
微笑
大笑
哭泣
惊讶
明显愤怒
```

 值得搜索。

 但是：

```
略显尴尬
隐藏的不耐烦
轻微紧张
犹豫
怀疑
```

 不要期望仅靠 embedding 得到特别可靠的结果。

 如果以后你的业务真的以“神态”为核心，可以再加一个专用 FER 模型作为结构化属性。

 第一阶段没必要。

 # 九、为什么不用一个向量，而要四种？

 考虑用户输入：

 > **“一个穿黑色夹克戴眼镜、面带微笑、正在打电话的男人。”**

 Global Frame 可能看到：

```
man
phone
street
```

 Person Context 更容易看到：

```
man
holding phone
phone near ear
```

 Person Tight 更容易看到：

```
black jacket
glasses
```

 Face 更容易看到：

```smiling
smiling
```

 于是最终不是：

```
Query ──→ 一个 Vector ──→ 一个 Index
```

 而是：

```
                         Global
                         ↑
                     scene/action

中文 Query → 分析 ──→ Person Context
                         ↑
                        action

                    Person Tight
                         ↑
                       clothing

                        Face
                         ↑
                     expression
```

 这对于你这个业务场景会比“换一个更强的 CLIP”重要得多。

 # 十、Query 也不要只 Embedding 一次

 例如用户输入：

 > 一个穿黑色连帽衫、戴眼镜、面带微笑正在打电话的年轻男性

 先保留原始 query：

```
Q0:
一个穿黑色连帽衫、戴眼镜、面带微笑正在打电话的年轻男性
```

 然后 Query Analyzer 拆成：

```
Subject:
年轻男性

Action:
男性正在打电话，手持手机靠近耳朵

Clothing:
男性穿黑色连帽衫

Accessory:
戴眼镜

Expression:
男性面带微笑
```

 然后分别编码。

 这里 Query Analyzer 不需要 VLM。

 一个小型中文 LLM 就足够，甚至早期 MVP 可以先通过 prompt + JSON schema 实现。

 输出例如：

```json
{
  "subject": "年轻男性",
  "action": ["正在打电话"],
  "clothing": ["黑色连帽衫"],
  "accessories": ["眼镜"],
  "expression": ["微笑"],
  "scene": [],
  "objects": ["手机"]
}
```

 # 十一、Qwen Embedding 的 Instruction 要固定

 Qwen3-VL-Embedding 是 instruction-aware 的。官方报告称，针对任务提供 instruction 通常可带来约 **1%～5%** 的提升，而且官方特别建议多语言场景中的 instruction 使用英文。[![image](https://www.google.com/s2/favicons?domain=https://huggingface.co&sz=128)huggingface.co](https://huggingface.co/Qwen/Qwen3-VL-Embedding-8B)

 所以不要每次随便写。

 例如整个系统固定：

```
Retrieve images that visually match the user's description,
with particular attention to visible human actions, body poses,
facial expressions, clothing types, colors, accessories,
objects, and scene context.
```

 Query 本身仍然使用中文：

```
一个穿黑色夹克、戴眼镜、正在打电话的男人
```

 也就是：

```
English instruction
+
Chinese query
```

 # 十二、召回策略

 不要一次搜索一个 collection。

 按照 Query Analyzer 的结果决定不同 view 的权重。

 例如纯动作：

 > “一个正在打电话的人”

 可以：

```
person_context    0.50
global            0.30
person_tight      0.15
face              0.05
```

 衣着：

 > “穿黑色皮夹克的人”

```
person_tight      0.55
person_context    0.25
global            0.15
face              0.05
```

 神态：

 > “一个正在笑的人”

```
face              0.55
person_tight      0.20
person_context    0.15
global            0.10
```

 复杂查询则动态组合。

 实际实现时不要直接把不同 collection 的 cosine similarity 生硬加起来，因为不同视图的 score distribution 会不同。

 推荐：

```
各索引 Top-K
      ↓
percentile / rank normalization
      ↓
Weighted Reciprocal Rank Fusion
      ↓
frame-level aggregation
```

 而不是单纯：

```
0.5 * cosineA + 0.3 * cosineB
```

---

 # 十三、第一次召回应多取一些

 Embedding 负责的是：

 > **Recall**

 不是最终判决。

 所以建议：

```
每个主要子 query：
Top 100~200

合并去重：
Top 300~500 frame candidates
```

 然后先做一次轻量 fusion：

```
300~500
   ↓
Top 50~100
```

 再交给：

 **Qwen3-VL-Reranker-8B**

---

 # 十四、Reranker 是整个系统第二个关键模型

 Qwen 官方实际上就是把两个模型设计成一套：

```
Qwen3-VL-Embedding
       ↓
大规模召回

Qwen3-VL-Reranker
       ↓
精细相关性判断
```

 Embedding 是 dual-tower：Query 与图片分别编码，可以预计算，因此适合千万级 ANN。

 Reranker 则是 single-tower / cross-attention，让 Query 与候选图片发生深层交互，因此计算昂贵，但对复杂细粒度匹配明显更适合。[![image](https://www.google.com/s2/favicons?domain=https://github.com&sz=128)GitHub](https://github.com/QwenLM/Qwen3-VL-Embedding)

 也就是说：

```
10,000,000 images
       ↓
Embedding
       ↓
300 candidates
       ↓
Reranker
       ↓
20 results
```

---

 # 十五、特别适合你的地方：Reranker 可以一次看多个 Crop

 Qwen3-VL 的输入接口支持单张或多张图片。[![image](https://www.google.com/s2/favicons?domain=https://github.com&sz=128)GitHub](https://github.com/QwenLM/Qwen3-VL-Embedding)

 所以对于一个 candidate，不必只给：

```
global frame
```

 可以构造：

```
Document:
[
    global_frame,
    person_context_crop,
    person_tight_crop,
    face_crop
]
```

 再让 Reranker 判断：

 > Query：“一个穿黑色夹克、戴眼镜、面带微笑、正在打电话的男人”

 它就可以同时检查：

```
Global
→ 是不是这个场景

Context crop
→ 是不是打电话

Person crop
→ 是不是黑色夹克 + 眼镜

Face crop
→ 是不是在笑
```

 这会比把所有信息压缩进一个 embedding 强得多。

 # 十六、视频抽帧策略也直接影响动作召回

 虽然你不需要 temporal modeling，但**抽帧频率仍然重要**。

 例如：

```
拿起手机
挥手
喝水
转头
比手势
```

 可能只持续 0.5～1 秒。

 如果固定：

```
0.2 FPS
```

 基本必然漏掉。

 我建议采用：

```
基础采样：1 FPS
+
Shot Boundary Sampling
+
高运动镜头：提高到 2 FPS
```

 第一版甚至可以直接：

```
1 FPS
```

 作为 baseline。

 之后根据数据做：

```
0.5 FPS
1 FPS
2 FPS
```

 的 Recall 对比。

---

 # 十七、相邻帧去重不要太激进

 比如：

```
10.0s  人没有笑
10.5s  人开始笑
11.0s  人笑
```

 对普通 image dedup 来说：

```
这三张图 95% 都一样
```

 但对你的业务：

```
10.0s ≠ 11.0s
```

 因为“神态”发生了变化。

 所以不要使用很激进的 SSIM / pHash：

```
相似 → 删除
```

 否则最先被删除的恰恰可能就是：

```
神态
手部动作
物体交互
```

 这种细节。

 只做：

 > 极端近重复 / 解码重复帧清理。

---

 # 十八、图像预处理

 Qwen3-VL-Embedding 官方当前实现允许动态像素配置，默认 `max_pixels` 为 1,843,200，约等于 1280×1440 量级，并推荐使用 BF16 + FlashAttention2。[![image](https://www.google.com/s2/favicons?domain=https://github.com&sz=128)GitHub](https://github.com/QwenLM/Qwen3-VL-Embedding)

 因此不要像老 CLIP 那样强制：

```
所有图像 → 224×224
```

 这会严重损失你关心的：

```
眼镜
表情
衣着纹理
手中的手机
```

 我建议：

 Global：

```
最长边 1280 左右
保持原始 aspect ratio
```

 Person：

```
尽可能保持原像素
不人为先缩成 224/336
```

 Face：

```
脸至少达到 80~100px 以上才值得独立索引
```

 如果原始脸只有：

```
18×18px
```

 即使放大到 512×512：

```
也不会凭空产生表情信息。
```

 # 十九、Person Detection

 这里不要做 open-vocabulary detection。

 你的目标固定：

```person
person
```

 因此使用快速稳定的人体 detector 就够了。

 流水线：

```
Frame
 ↓
Person Detector
 ↓
bbox + confidence
```

 只对：

```
confidence > threshold
```

 生成 Person Crop。

 建议：

```
tight_bbox
context_bbox = expand(bbox, 1.3~1.5)
```

 不要为每个通用物体都生成 embedding，否则向量数量会爆炸。

 第一版只处理：

```
Global
Person Context
Person Tight
Face
```

 足够。

---

 # 二十、Face Detection

 对于 Person Crop 再进行：

```
Face Detector
```

 而不是直接在整个 4K Frame 上找。

 然后检查：

```
bbox size
blur
confidence
occlusion
```

 太小/太糊直接不建 Face embedding。

 这可以避免：

```
垃圾向量
```

 污染 Face Index。

 # 二十一、向量维数选择

 Qwen3-VL-Embedding-8B 原始最高：

```
4096 dimensions
```

 但我不建议生产第一版直接全部存 4096。

 因为如果：

```
10M vectors
×
4096
×
4 byte FP32
```

 单裸向量就是：

```
≈ 164 GB
```

 还没算 HNSW。

 我建议默认：

 > **2048 dimensions**

 这是精度优先但仍比较可控的配置。

 因为它支持 MRL，所以可以直接截断 embedding。官方支持自定义 64～4096 维。[![image](https://www.google.com/s2/favicons?domain=https://huggingface.co&sz=128)huggingface.co](https://huggingface.co/Qwen/Qwen3-VL-Embedding-8B)

 实际测试：

```
1024
2048
4096
```

 三个版本。

 如果：

```
2048 vs 4096
R@10 差距 < 0.5%
```

 就没有理由存 4096。

 我建议不是四个完全不同 collection，而是两个：

 `frame_global`：

```

=
1 vector
```

 `visual_regions`：


 这样可以通过：

```

```

 # 二十四、一帧最终大概产生多少 vector？

 假设平均：

```
1 frame
1 person
1 visible face
```

 那么：

```
Global          1
Person Context  1
Person Tight    1
Face            1

≈ 4 vectors/frame
```

 1000 小时视频、1 FPS：

```
3,600,000 frames
```

 理论上可能达到：

```
~10M–14M vectors
```

 具体取决于人物出现率。

 这就是为什么不能无脑用：

```
4096 float32
```

 # 二十六、在线 Query 完整执行流程

 假设：

 > “找穿蓝色衬衫、戴眼镜、正在笑着打电话的男性。”

 ### Step 1：Query Analysis

 得到：

```

男性

clothing:
蓝色衬衫

accessory:
眼镜

expression:
微笑

action:
打电话

object:
```

```
C:
+ Person Tight

+ Face
```

 你很可能会看到：

```

 ↓
```

 这能非常明确地证明每个系统模块到底值不值得它的算力成本。

 # 三十六、最终推荐版本

 所以如果今天让我实际落地，我会明确选：

 | Layer | 最终方案 |
| --- | --- |
| Core Embedding | Qwen3-VL-Embedding-8B |
| Embedding Dim | 2048，A/B 1024/4096 |
| Similarity | Cosine / normalized dot product |
| Reranker | Qwen3-VL-Reranker-8B |
| Query | 中文 |
| Instruction | 英文固定 instruction |
| Frame Sampling | 1 FPS baseline + shot/adaptive sampling |
| Global Index | ✓ |
| Person Context Index | ✓ 强烈建议 |
| Person Tight Index | ✓ 强烈建议 |
| Face Index | ✓ 神态搜索必需 |
| Video Temporal Model | 不需要 |
| Vector DB | Qdrant |
| Metadata | PostgreSQL |
| Media Storage | MinIO/S3 |
| Video Decode | FFmpeg/PyAV |
| Serving | vLLM pooling |
| API | FastAPI/gRPC |
| GPU | 开发 32GB；生产推荐 2×48GB |
| Query Strategy | Query decomposition + Multi-index Recall |
| Final Ranking | Multi-image Qwen3-VL-Reranker |

 最终系统的核心思想并不是：

 > **“找一个最强的 image embedding model。”**

 而是：

 > **“用当前强的中文多模态 embedding 做高召回，再通过针对人物细粒度属性设计的多尺度视觉索引保住信息，最后用跨模态 reranker 解决多个条件同时成立的问题。”**

 对你现在提出的 **动作 + 神态 + 衣着类型 + 中文 Query**，这会是我目前最推荐的整体架构。

 如果模型继续快速更新，这套架构本身也不需要推倒重来，只替换 Embedding/Reranker 层即可。

 我也可以持续跟踪 Qwen3-VL-Embedding、SigLIP/Jina 等替代模型的新 benchmark 和版本变化。
